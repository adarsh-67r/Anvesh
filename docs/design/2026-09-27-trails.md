# Trails: topic-level learning from YouTube

Status: design approved in discussion, awaiting spec review · 2026-09-27

## Problem

A whole YouTube playlist is one skill today. Striver's A2Z DSA playlist (316 lectures, arrays through DP) gets a single mastery score and one pool of practice questions, and those questions are written from the skill name and lesson titles, not from what the lectures teach. A student who has watched the binary search lectures is quizzed on anything in the playlist, and long videos that cover several topics are treated as one lesson.

Two further defects surfaced during design:

- Skills are global. The recommender, `/graph`, todos and the quiz game all run `select(Skill)`, so every student sees skills that other students imported.
- Generated questions live in an in-memory cache and are lost on every Render restart, so IRT never sees a stable question id.

## Goal

Turn any YouTube playlist or video into a **trail**: an ordered map of topics, each built from the lectures that teach it, with practice, quizzes and tutor answers grounded in those lectures. Mastery and recommendations work per topic.

Out of scope: PDF/PPT sources, teacher features, tappable timestamps in tutor replies, translated notes (the Hindi work comes later), sharing a trail with other students.

## Concepts

```
Trail "DSA Placements"                 personal: one student, one subject
 ├─ Sources   playlists and single videos
 └─ Topics    Arrays → Hashing → Binary Search → … → Graphs → DP
      └─ Lessons   a whole short video, or a timed part of a long one
```

- **Topics are `Skill` rows.** The recommendation engine keeps operating on skills; its algorithms and interface do not change.
- **Topics are shared, trails are personal.** A playlist's topic plan is built once and reused by every student who imports it, so answers pool across students and BKT/IRT can activate. Mastery stays per student.
- **Each video is read once, ever.** Lecture text and topic notes are cached globally.

## Data model

| Table | Status | Fields |
|---|---|---|
| `trails` | new | id, user_id, title, created_at |
| `sources` | new | id, trail_id, kind (`playlist`/`video`), url, source_ref (playlist or video id), plan_version, title, status (`importing`/`ready`/`failed`), error, updated_at |
| `topic_plans` | new, shared | source_ref, version, method (`gemini`/`chunked`), created_at. PK (source_ref, version) |
| `trail_topics` | new | trail_id, skill_id, position, prerequisites_override (JSON list or null), equivalent_to (JSON list of skill ids in the same trail). PK (trail_id, skill_id) |
| `skills` | changed | + `source_ref`, `plan_version`, `position`, `summary`. Ids are `{source_ref}:v{version}:{n}`: stable, title-independent (Hindi titles slugify to nothing), and under the 100-char limit |
| `skill_videos` | changed | + `youtube_id`, `start_sec`, `end_sec` (null = whole video), `duration`; `user_id` becomes nullable: null for imported lessons, set for lessons a student adds by hand |
| `video_context` | new, shared | youtube_id, start_sec, end_sec, text (timestamped lines, **absolute video time**), method (`captions`/`gemini`/`titles`), created_at |
| `topic_notes` | new, shared | skill_id (PK), status (`preparing`/`ready`/`failed`), summary, concepts (JSON: concept, explanation, lesson_id, timestamp_sec), method, progress, updated_at |
| `questions` | new, shared | id = sha1(skill_id + text) so identical wording in two topics cannot collide; skill_id, lesson_id, concept, text, options (JSON), answer, explanation, timestamp_sec, created_at |

Visibility rules: a student sees imported lessons plus lessons they added themselves, never another student's manual additions. Prerequisite edits never touch the shared `skills.prerequisites`; they write `trail_topics.prerequisites_override` (see Recommendation engine).

## Import: playlist to topics

Endpoints: `POST /api/trails {title, url}` creates a trail and its first source; `POST /api/trails/{id}/sources {url}` adds a source. Import runs as a background task; the app polls `GET /api/trails/{id}` for source status.

0. **Duplicate check.** A source already in any of the student's trails is refused ("Already in your DSA Trail"). One topic therefore never sits in two of a student's trails, which keeps prerequisite overrides unambiguous.
1. **Reuse check.** If a plan exists for this `source_ref`, link its latest version's topics into the trail (`trail_topics`) and mark the source `ready`. No YouTube or Gemini calls.
2. **List items.** yt-dlp flat extraction for a playlist (titles, ids, durations); full extraction for a single video.
3. **Chapters for long videos.** For videos over 45 minutes, fetch chapters (concurrency 4). Each chapter becomes an item with start/end. No chapters or a blocked fetch keeps the video as one item.
4. **Topic plan.** One Gemini call (FAST config) with the ordered items. Returns topics: title, one-line summary, item indices, prerequisite topic indices. When adding to a trail that has topics, the prompt includes their titles so cross-source prerequisites can be proposed; those go to `trail_topics.prerequisites_override` for this trail only, since the shared plan must not depend on another source.
   - **Overlap.** In the same call, Gemini marks which new topics teach the same thing as an existing topic in the trail (Luv's "Binary Search" ≈ Striver's "Binary Search"). Matches are stored symmetrically in `trail_topics.equivalent_to` on both sides. They are per trail, because whether two playlists overlap depends on which playlists a trail holds. When a plan is reused (step 1), overlap detection still runs as its own small Gemini call against the trail's existing topics.
5. **Validation (pure function, unit-tested).** Every item in exactly one topic, orphans attached to the nearest topic, order preserved, prerequisites only point to earlier topics (acyclic). On Gemini failure or invalid output: chunks of 8 items in order, titled from their first lesson, chained linearly.
6. **Save** a `topic_plans` row (method `gemini` or `chunked`), its skills and lessons, and `trail_topics`; the source becomes `ready` with its topic count. Saving happens in one transaction so a crash never leaves half a plan.

**Rebuild topics** (trail screen action) builds a new plan version for that source and moves only this trail's `trail_topics` to it. Other students keep the version they have until they rebuild, so nobody's map changes underneath them. This also covers a playlist that has grown since its plan was built, and a plan that fell back to `chunked` because Gemini was down. Reuse picks the latest `gemini` version over a `chunked` one.

**Delete trail** removes its `trail_topics` and `sources`; shared topics, notes and questions stay for other students.

Failures mark the source `failed` with the reason and keep the trail intact; the app offers Retry.

**Background work and restarts.** Import and grounding run as in-process tasks, which die if Render restarts or redeploys mid-job. Every job row carries `updated_at`, bumped as work progresses; a `sources` row stuck in `importing` or a `topic_notes` row stuck in `preparing` for more than 5 minutes is treated as dead and restarted by the next request that touches it. Blocking yt-dlp calls run in `asyncio.to_thread` so they never stall the event loop.

## Grounding: lectures to notes to questions

Trigger: `GET /api/topics/{skill_id}/notes`, allowed only for topics in the caller's trails. Ready notes return immediately. Otherwise one background job per topic starts and the endpoint returns `{status: "preparing", progress}`; the app polls every 3 s. Single-flight is enforced by the database, not memory: the job claims the topic with `INSERT … ON CONFLICT DO NOTHING` on `topic_notes`, so two simultaneous requests cannot both start it.

**Lecture text per lesson**, cheapest first:

1. **Cache.** `video_context` for the same youtube_id and range, or a whole-video entry sliced to the range.
2. **Subtitles.** yt-dlp subtitles, manual then automatic, language order en, hi, then any; timestamps kept; sliced to the lesson range.
3. **Gemini watching.** YouTube URL input at low media resolution, prompted for timestamped lecture notes, limited to the lesson's range. Clipping YouTube input by offset is not documented and is verified in the first implementation task; if unsupported, videos over 2 hours skip this step. Timestamps Gemini returns for a clip are relative to the clip, so `start_sec` is added before saving; everything stored is absolute video time. A daily budget guard stops at 7 of the free tier's 8 video-hours per day; usage is computed from today's `video_context` rows with method `gemini`, so it survives restarts.
4. **Titles only.** The current behaviour; the topic is marked `method = titles` and the app labels it.

**Topic notes.** One Gemini FAST call over the topic's lecture text (truncated per lesson to a fixed budget): summary plus 8–15 key concepts, each tied to a lesson and timestamp.

**Questions.** Generated from the notes, 12 per topic initially, each tied to a concept, lesson and timestamp and stored in `questions`. Practice serves 5 the student has not answered recently (from their `learning_events` question ids) and tops up the bank when a student exhausts it, up to 60 per topic; past that, the least recently seen questions repeat. Top-ups pass existing question texts to Gemini to avoid near-duplicates, and exact duplicates are dropped by id. Lesson quick checks draw 2–3 questions for that lesson. The Challenge quiz game draws from the same bank, replacing its in-memory cache. The explanation of a wrong answer links to the lesson at `timestamp_sec`.

**Tutor.** A `topic_id` on `/api/chat` adds that topic's notes (not raw transcripts) to the system prompt, with an instruction to answer from the lectures and cite lesson and timestamp.

Expected first-open time: about 10–20 s with subtitles, 30–60 s with Gemini watching. Every later open, by any student, is instant.

## Recommendation engine

- New helper `user_skills(db, user_id)`: topics in the student's trails. Each topic's prerequisites are its `prerequisites_override` when set, otherwise the shared plan's; prerequisites pointing outside the student's trails are dropped so nothing is locked behind a topic they cannot see. It replaces every bare `select(Skill)` (orchestrator, recommend router, todos, game).
- **Overlapping topics.** `equivalent_to` links form groups (transitively, so A≈B and B≈C is one group). A topic counts as mastered for unlocking and recommendation when any topic in its group is mastered, and a prerequisite on any group member is satisfied by any other. Recommendations never offer two topics from the same group at once; the one with more progress, then the earlier position, is offered. Each topic keeps its own mastery and events, so pooled BKT/IRT data per playlist stays clean.
- The prerequisite editor on the topic screen writes `prerequisites_override` for the student's trail, validated acyclic against that student's graph. It no longer edits the shared skill, which would change every student's map.
- `/recommend/answer`, practice, quiz and notes endpoints reject topics outside the caller's trails, so one student cannot pollute another playlist's pooled data.
- EMA/BKT/IRT, the frontier, prerequisites and dropout risk are unchanged. BKT activates at 200 responses per topic and IRT at 200 responses from 10 students; because topics are shared per playlist, those counts pool across everyone studying that playlist. In a small demo the engine will show EMA, which the topic screen already states.
- Answers carry the stable `questions.id`, giving IRT consistent item ids.
- `/recommend/next` returns the trail title with each recommendation for the Today card.

## App

- **Sidebar:** Today, Trails, Review, AI Tutor, Focus Timer, Tasks, Study Groups. "My Path" and "Add Topic" are removed.
- **Trails list:** cards with name, source count, topics-mastered bar, next topic; "New trail"; empty state prompting for a playlist link.
- **New trail:** name plus first URL; opens the trail with live import status.
- **Trail screen:** the levelled topic map (current My Path UI) and a Sources list with status, Retry and "Add source".
- **Overlap on the map:** a topic with an equivalent shows "Also in Luv's playlist"; once its group is mastered through the other topic it shows "Covered" instead of Ready.
- **Topic screen:** summary and key concepts once grounded, a "From the lectures" / "From lesson titles" badge, a **"Test out · 5 questions"** action on topics that have an equivalent (a normal practice session, framed as a quick check), lessons showing time ranges for video parts, Practice and Challenge as today.
- **Lesson page:** player starts and stops at the part's range; key concepts for the lesson; "Check your understanding" quick check; up next.
- **Practice:** "Reading the lectures… n of m lessons" while preparing; "Watch again · Lesson n at mm:ss" on wrong answers.
- **Today:** recommendation names its trail. **Tutor:** header shows topic and trail when opened from one.

## Migration

One Alembic revision, run locally against Supabase:

- Create the new tables and columns.
- For each user who owns lessons (`skill_videos.user_id`): create "My first trail", one source per distinct `skills.source_url` with a `topic_plans` row of version 0 (method `chunked`), and `trail_topics` rows for those skills. Existing skill ids, mastery, events and flashcards are untouched. A skill two users imported is linked into both trails.
- Existing `skill_videos` keep their `user_id`; the migration nulls it for lessons that came from a playlist import, so they stay visible to everyone linked to that topic.
- Migrated playlists keep their whole-playlist topic until "Rebuild topics" creates version 1 with the new pipeline. Rebuilt topics get new ids, so old mastery for the whole-playlist skill stays in history but no longer drives recommendations.
- The migration is tested on a copy of the schema locally before it runs against Supabase.

## Known limits

- In a small demo BKT and IRT stay inactive; the 200-response thresholds are deliberate.
- Subtitle fetching from Render's network is unverified and may be blocked by YouTube; Gemini watching is the fallback, bounded by the 8 free video-hours per day.
- Plans are built from titles and chapters. A long video without chapters stays one lesson even if it spans several topics; its notes still cover everything it teaches.
- A playlist that grows after import keeps its old plan until someone runs Rebuild topics.

## Errors

| Failure | Behaviour |
|---|---|
| Import step fails | Source `failed` with reason and Retry; trail keeps what succeeded |
| Gemini unavailable | Existing retries and fallback model, then the chunked plan or title-only questions |
| YouTube blocks subtitles | Gemini watching, then titles only past the daily budget |
| Private or removed video | Lesson marked unavailable; the rest of the topic is unaffected |
